**Embedded systems & hardware security engineer** · PhD, University of Huddersfield (2026)

I build and test low-power embedded systems — firmware, PCBs and the measurements that show whether they really work. My PhD developed hardware-rooted device authentication for LoRaWAN IoT nodes, combining SRAM Physical Unclonable Functions with RF fingerprinting on ARM Cortex-M0+ hardware. Alongside it I build embedded security projects end to end, from bootloader to radio link, each with host-side tests and its evidence kept in the repository. I verify small digital designs in two hardware description languages, and I check the tests themselves by breaking the circuits on purpose. I also test machine learning for small devices, with evaluation designed so that the test data cannot flatter the result.

### Projects
**Finished**
- 🔐 [**STM32L0 FreeRTOS sensor node with a custom secure bootloader**](https://github.com/baliyu/stm32l0-freertos-sensor-node) — FreeRTOS LoRa node with an AES-CTR/CMAC link and replay protection. Own bootloader that checks an ECDSA P-256 signature, refuses downgrades and installs updates safely (power cut simulated at 1,682 points of an install). Bootloader write-protected, read-out protection Level 1, and a boot-time check that halts if the protection is weakened. Limitations written up honestly.
- 🔑 [**MKR WAN 1310 secure-element LoRa node**](https://github.com/baliyu/mkrwan-secure-element-node) — link keys held in an ATECC608 that never reveals them. AES-CTR and CMAC are built from the chip's single-block AES: byte-identical to my software implementation on 2,000 random packets and accepted by the unchanged receiver. Hardware counter as frame counter, and a comparison with SRAM PUFs.
- 📡 [**Zephyr BLE vibration monitor**](https://github.com/baliyu/zephyr-ble-vibration-monitor) on the Arduino Nano 33 BLE — 400 Hz accelerometer sampling, CMSIS-DSP FFT for the dominant frequency, BLE notifications readable only after authenticated pairing (passkey on the USB console, bonds kept in flash), 44 ztest cases on native_sim, and GitHub Actions CI that runs them and builds the firmware on every push. Verified on the board with an iPhone.
- 🧩 [**RTL verification lab**](https://github.com/baliyu/rtl-verification-lab) — a UART (transmitter, receiver, loopback), an SPI master (all four modes) and an asynchronous FIFO between two unrelated clocks, each written twice, in Verilog and in VHDL, and checked by one shared set of Python (cocotb) tests on Icarus Verilog and GHDL: 30 simulator runs on every push in GitHub Actions. The SPI tests use a slave built from the published table of the four modes, not from my own circuit. The tests are checked by breaking the circuits on purpose: 48 bugs, each in both languages (96 broken circuits), of which 90 are caught; the 6 that survive are three cases that ordinary RTL simulation cannot see, each listed in the README with the reason. For the FIFO, a test stand-in for the synchroniser that lets changing bits arrive at random times shows that Gray-coded pointers survive, while the same design with plain binary pointers passes an ordinary simulation and is caught only by that stand-in. Simulation only: no FPGA board.
- 🎛️ [**pid-control-lab**](https://github.com/baliyu/pid-control-lab) — a fixed-point PID controller and a sensor-fault supervisor in C for the Cortex-M0+ (no floating-point unit). Seven closed-loop requirements were written down as numbers before the results (step response, 27 different plants, sensor noise, a load disturbance, windup, a failed sensor), checked by 181 tests built with the undefined-behaviour sanitiser, so an integer overflow fails the test that causes it. The gains come from a measured plant model, not from guessing. Then the same controller ran on an Adafruit Feather M0 (SAMD21) driving a real circuit, a DAC into a 100 kΩ and 100 nF filter read back by the ADC, with the loop sped up to match the faster plant. The PC model predicted a time constant of 10 ms and the board measured 10.5 ms; the closed-loop step to 2000 counts settled in 41 ms with an average error of −0.07 counts from the target, which meets the requirement scaled for the faster plant. The first capture was a floating input (50 Hz mains hum), which exposed and fixed a weakness in my plant-fitting tool; the real captures, the generated predicted-against-measured table and the tests that tie the documentation to the data are in the repository. Built with AI assistance (Claude); I wired and ran the hardware, captured and analysed the measurements, and chose the gains from them. Limits, stated in the repository: an electrical stand-in, not a heater; one board and one circuit; a port to an STM32 not done.

**In progress**
- 🧪 [**tinyml-edge-lab**](https://github.com/baliyu/tinyml-edge-lab) — tested building blocks for machine learning on my own boards, with evaluation designed not to flatter the model.
  - **Held-out results.** UCI activity data (cross-validation grouped by volunteer, the nine test volunteers used once per model): a 33-node decision tree scores 0.834 macro-F1 and a 2,186-node random forest 0.877. CWRU bearings: a forest scores 0.989 on a random split of windows, 0.943 holding out a motor load and 0.332 — chance — holding out a fault size, reported as it came out. My own SparkFun Edge recordings (5 desk gestures, 3 sessions, 465 windows): a forest scores 0.918 on a session it never saw, against 1.000 on a random split.
  - **On the device.** Decision trees export to C with float thresholds that keep every split exact; a 33-node tree is 744 bytes of flash on a Cortex-M0+ (measured with the ARM compiler). The gesture features in C take 1.5 KB of flash and match the Python ones: no trained model changed an answer on any of the 465 windows. The whole chain (resampling to 50 Hz, windows, features, a 100-tree forest) runs on the Edge at 3.8 ms per window, measured on the chip; the repository has the firmware, a serial monitor and a host-side simulation of the firmware's loop.
  - **Live accuracy on the board.** A new sitting, recorded after the model was trained: 15 shuffled blocks of one gesture each (7 minutes), with the board's own predictions scored against the gesture shown. 0.967 accuracy and 0.967 macro-F1 over 180 windows (95 % interval 0.922 to 1.000, resampling whole blocks; chance is 0.200). Weakest gesture: circle, recall 0.889 (4 of 36 windows read as tilt). The same model type scored 0.918 when a whole session was held out offline.
  - **Limits, stated in the repository:** one person, one board and one live sitting, so the numbers say little about others, and the interval is wide because there are only three blocks per gesture. The board also reported one overwritten sensor sample, which I have not explained.
